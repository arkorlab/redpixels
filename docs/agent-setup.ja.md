# エージェントによる redpixels のセットアップ

[English](agent-setup.md) | **日本語** · [README](../README.ja.md)

このガイドは、redpixels のデプロイと既存の Gmail 下書き作成フローへの接続を依頼されたエージェント向けです。ユーザーの依頼と、実行環境のアカウントアクセス・承認ルールに従ってください。この文書だけでアカウントへのアクセスやメール送信が許可されるわけではありません。

ユーザーのプロンプトで選んだ [cf の手順](agent-setup-cf.ja.md)または [Wrangler の手順](agent-setup-wrangler.ja.md)を使います。両方の設定を同梱しています。希望のない新規導入には cf（現在ベータ）を案内し、既存の導入ではユーザーが切り替えを選ばない限り CLI を維持します。無断で CLI を変更したり、移行処理を実行したりしません。

README のプロンプトは、用途を明記した自分宛ての確認用下書き 1 通を依頼します。人が Gmail で確認して Send を押します。同梱の Gmail CLI に送信コマンドはありません。

セルフホストの Gmail 連携は、[自分の Google Cloud OAuth クライアントを使う CLI の設定手順](agent-setup-gmail.ja.md)を標準にします。初期プロンプト、本人への引き継ぎ、料金、復旧、次回以降の操作も同ガイドにあります。利用者がこのセットアップを依頼済みなら、各工程で同じ方式の選択を繰り返し求めず、既存の認証・設定を確認して進めます。[既存の Gmail 接続](gmail-connectors.ja.md)は、利用可能な MIME 経路を実際に確認できる場合の任意の短縮経路です。

## セットアップ完了に必要なもの

- ユーザー自身の Cloudflare アカウントにある Worker・SQLite Durable Object と、認証付きの履歴 API。
- エージェントが作る HTML Gmail 下書きへ、新しいピクセルを追加する永続的な設定。
- 画像取得と人による閲覧を区別して報告する動作確認。
- 受信先を設定した場合の署名付き Webhook。未設定の場合は **履歴は有効、Webhook は無効** と明示。

redpixels は API を使うツールです。デプロイだけで Gmail の動作が変わったり、ピクセルのない通常メールを自動追跡したりはしません。Gmail 認証は下書き作成エージェントや手元のクライアントで扱い、Worker には渡しません。

Google Cloud の設定を完了しても、Gmail で一から作成したメールへの自動挿入や、Sent の自動検知は追加されません。現在の既定の手順には、送信したとの申告後の手動 `arm` が必要です。この未実装部分を設定だけで解決したと報告しないでください。将来の Managed 版は運営側が OAuth を管理する方向ですが、現在提供している機能ではありません。

## 1. 環境とデプロイ先を確認する

1. 最新の [README](../README.ja.md)、`package.json`、選んだ CLI の設定を読みます。必要なら `https://github.com/arkorlab/redpixels.git` を clone し、既存の作業場所や無関係な変更は保持します。
2. 必要な Node.js・pnpm のバージョンを確認し、`pnpm install --frozen-lockfile` を実行します。プロジェクトに固定された CLI を使います。cf は Node.js 22.18 以降が必要で、Bun には対応しません。
3. 選んだ CLI の既存の認証を使います。cf と Wrangler の OAuth ログインは別管理です。認証したユーザーと対象アカウントを確認し、複数ある場合は選択を求めます。同名の `redpixels` Worker が存在する場合は内容を確認し、別用途の Worker との名前の衝突はユーザーと解決します。
4. 認証がない場合は選んだ CLI の公式の手順を使います。両方のガイドに localhost のコールバックが使えない場合のデバイス認証を記載しています。ユーザーが許可する間はログイン処理を動かしたままにします。Worker のデプロイに必要なアクセスを使い、実行環境の承認ルールに従います。
5. [Gmail・Google Cloud セットアップ](agent-setup-gmail.ja.md)に従い、既存の認証情報・専用プロジェクトがあれば再利用します。なければ専用プロジェクトで Gmail API・最小の `gmail.compose`・Desktop OAuth を設定し、保護した JSON と OS の認証情報ストアを使います。課金・カード・無料トライアル・追加サービスを設定しません。本人確認・規約・アクセス許可・環境の承認で本人操作が必要なときだけ具体的に引き継ぎます。独立して進められるデプロイは続けます。既存の Gmail 接続を使う場合は [MIME の互換性](gmail-connectors.ja.md)を確認し、内部トークンは取り出しません。秘密の値をチャットへ貼らせないでください。

## 2. デプロイして設定を保存する

暗号学的に安全な乱数で 32 文字以上の `API_TOKEN` を生成します。例は 32 バイトの乱数を hex にした値です。途中から再開する場合は既存の鍵を使います。エージェントのシークレット管理機能か、Git から除外した保護されたローカルファイルに保存し、値ではなく保存場所を報告します。

cf 用の `cloudflare.config.ts` は SQLite Durable Object の export を、Wrangler 用の `wrangler.toml` は対応するマイグレーションを宣言します。手動のデータベース ID は不要です。個人のアカウント ID やドメインをコミットする必要もありません。個人設定は環境変数に置きます。Cloudflare の現在のプランを使ってください。[SQLite Durable Objects は Workers の無料・有料プランで利用できます](https://developers.cloudflare.com/durable-objects/platform/pricing/)が、各プランの制限は適用されます。

固定された両 CLI は、保護されたファイルからデプロイと同時にシークレットを設定できます。**どちらか一方**を実行します。

```sh
# cf
pnpm run deploy:cf --secrets-file .env.redpixels.json
# または Wrangler
pnpm run deploy:wrangler --secrets-file .env.redpixels.json
```

`.env.redpixels.json` は、`API_TOKEN` と必要に応じた Webhook 設定など、Worker 用の値を **安全に作成しておくファイル** です。新規導入時は `node --experimental-strip-types examples/create-secrets.mts` で、鍵を表示せずに生成し、権限 0600 のファイルを作れます。既存ファイルは上書きしません。Git の除外対象であることを確認してください。Cloudflare API や Gmail の認証情報は含めません。値の更新方法は選んだ CLI のガイドを参照し、値をログやコマンド引数に出さないでください。

下書き作成エージェントのシークレット設定に `REDPIXELS_URL` と `REDPIXELS_API_TOKEN` を保存します。後者の値は Worker の `API_TOKEN` と同じです。Worker 用シークレットのファイルと、Gmail 認証情報・手元のエージェント専用設定を分けます。

`/` が redpixels を返すこと、認証なしの `/v1/messages` が `401`、認証付きの同じリクエストが `200` になることを確認します。

## 3. エージェントの Gmail 下書き作成フローに接続する

[Gmail CLI](gmail-cli.ja.md)を使い、[詳しい初期設定](agent-setup-gmail.ja.md)から実際のトークン更新・下書き保存・MIME 検証まで進めます。`auth status` の接続済み表示は保存情報の有無であり、現在のトークンの有効性の証明ではありません。既存コネクターを使う場合も、画像を除去する入力欄へ同じ HTML を繰り返し渡さず、その経路の保存済み MIME を確認してください。[低水準サンプル](../examples/gmail-draft.mts)は認証や更新を自分で管理する場合向けです。

次の動作をユーザーの下書き作成フローや永続指示へ保存し、鍵の値は参照で扱います。

```text
追跡付き Gmail 下書きを作るとき:
1. 保存済みの redpixels 環境設定・Gmail アカウント・状態ディレクトリを使う。
2. UTF-8 HTML と論理的なメールごとに安定した --operation を用意する。
3. pnpm --silent gmail draft --to ADDRESS --subject SUBJECT --html FILE
   --operation OPERATION を実行する。既定は armed:false。
4. state:verified と追跡 ID・Gmail 下書き ID・メッセージ ID・検証時刻を保存する。
   画像を確認できなければ連携未完了とし、送信や追跡成功の扱いをしない。
5. 編集後は pnpm --silent gmail verify --operation OPERATION で再確認する。
6. 送信は本人が Gmail で行う。送信済みとの申告後に
   pnpm --silent gmail arm --operation OPERATION --confirm-sent を実行する。
7. 作成結果が不明なら status と Gmail を調べ、同じ操作を盲目的に複製しない。
```

任意の既存コネクター経路では、安定した Idempotency-Key と `armed:false` で登録し、返された `pixel_html` を対応する MIME / raw 入力へ挿入します。保存済みの画像と各 ID を確認し、申告後に `POST /v1/messages/<id>/arm` を呼びます。この経路には CLI の操作記録はないため、独自に対応と不明状態を保持してください。既存接続を利用できることだけで画像保持や配信を保証しません。

受信者を分けて追跡する場合はメールとピクセルも分けます。Gmail の下書き ID は安定していますが、その中のメッセージ ID は下書きを置き換えると変わります。redpixels の登録の重複防止は Gmail の下書き作成や送信を重複防止するものではないため、結果が不明な場合は調べてから再試行します。

設定を保存したファイルや項目の正確な場所を記録してください。環境変数を置くだけでは、今後の下書き作成の動作は変わりません。永続設定ができない環境では上の指示を渡し、**手動での組み込みが必要** と明示します。

新しい CLI は既定で `armed:false` と送信後の手動追跡開始を使います。従来の HTTP API と低水準サンプルは即時追跡を維持し、CLI では `--armed` で明示的に即時追跡を選べます。開始前の取得も履歴には残ること、送信直後の取得を逃す場合があること、キャッシュを解消できないことを説明します。Gmail の送信済み監視や定期実行を勝手に追加しないでください。

## 4. 受信先がある場合は Webhook を設定する

`WEBHOOK_URL` と、別の 32 文字以上のランダムな `WEBHOOK_SECRET` を設定します。`WEBHOOK_MODE`（`first` / `every`）と `WEBHOOK_FILTER`（`all` / `unflagged`）はユーザー指定を使い、指定がなければ README の既定値を維持します。

HTTPS 受信先は redpixels の JSON と、raw body の HMAC・時刻・イベント ID の検証に対応している必要があります。[署名検証サンプル](../examples/verify-webhook.mts)を再利用できます。通知サービスの任意の URL は、本文形式を変換する処理が必要な場合があります。ユーザーが管理する受信先を使ってください。

受信先がなければ履歴の追跡までを完了し、後から Webhook を追加する方法を説明します。確認できていない通知設定や受信を成功扱いしないでください。

## 5. 動作確認と報告

1. `pnpm check`、`pnpm test`、選んだ CLI のビルド dry run（`pnpm run build:cf` または `pnpm run build:wrangler`）を実行します。これらはメールを送らず、Gmail の実環境での互換性を確認するものでもありません。保守時は両方をビルドした後、`pnpm run check:cli-builds` で実行コードとストレージ設定を比較できます。
2. 用途を明示した人工的なテストを登録します。公開ピクセルを API の Authorization ヘッダーや所有者 Cookie なしで取得し、認証付き履歴を確認します。HEAD だけでは記録されません。人の既読と扱わないでください。通知を有効にした場合は通知対象かどうかも確認し、受信側で署名検証と受理を確認します。フィルターで正しく除外される場合もあります。
3. 標準の直接 CLI、または利用者が選んだ既存コネクター経路で、用途を明記した新規の確認用下書きを作り、保存済み raw MIME の画像を確認します。別のテスト宛先が指定されていなければ、認証済みの自分のアドレスを使います。人が Gmail で確認して Send を押し、その申告後に追跡を開始します。CLI ガイドの手動受入試験では別の受信アカウントを推奨します。送信の受付は受信箱への到達の証明ではありません。
4. 取得・通知件数の基準値を記録してから、受信メールをユーザーに開いてもらいます。新しいイベント ID・時刻・回数・フラグ・配信状態を照合し、受信先があれば署名も確認します。既存の権限で受信 MIME を確認できる場合は確認し、できなければ未確認と記録します。
5. [既存コネクターの試験](gmail-connectors.ja.md)は新しい未送信下書きの保存確認までです。各経路の検証範囲を区別してください。新CLIの Web / iOS 受入試験は [CLI ガイドの手動手順](gmail-cli.ja.md#手動の受入テスト)を使います。従来の[実機の記録](mobile-test.md)は別の下書き作成経路を使っており、新CLIの検証を代替しません。モバイル互換性は同記録も参照してください。実際に操作した端末・アプリを明記し、人工的な取得や単体テストを実機確認の代わりにしないでください。

選んだ CLI・バージョン・設定ファイル、Worker の URL とアカウント・名前、シークレットの保存場所、下書き作成の永続設定の保存場所、テストの ID・結果、Webhook の状態、不足するアクセスを短く報告します。秘密の値は含めません。

精度の限界も説明してください。下書きのプレビューやバックグラウンド通信でも通知が発生し、フラグが空でも人の既読とは限りません。プロキシは本人の識別や再開封を隠すことがあります。有効な署名が保証するのは通知の真正性であり、人が読んだことではありません。デプロイだけで全体を完了扱いせず、各工程を確認済み・未完了・利用不可として報告します。
